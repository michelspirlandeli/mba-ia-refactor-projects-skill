  #1 [CRITICAL] Credenciais hardcoded (AP-02)

  File: app.py:13 · services/notification_service.py:7-10
  Description: SECRET_KEY = 'super-secret-key-123'; SMTP taskmanager@gmail.com /
  'senha123'.
  Impact: Quem tem o repositório tem a chave de sessão e a senha do e-mail, e
  não dá para trocá-las por ambiente.
  Recommendation: config.py lendo variáveis de ambiente + .env.example (P-02).

  #2 [CRITICAL] Exposição de dados sensíveis (AP-05)

  File: models/user.py:16-25 · routes/user_routes.py:33, 85, 129, 209
  Description: User.to_dict() serializa 'password' (hash MD5). Isso vaza em GET 
  /users/<id>, POST /users, PUT /users/<id> e na resposta do POST /login.
  Impact: Hash MD5 sem salt é revertido na hora (as senhas do seed são 1234,
  abcd e pass).
  Recommendation: Tirar password de qualquer serialização pública (P-05).

  #3 [CRITICAL] Sem autenticação/autorização (AP-03)

  File: routes/user_routes.py:42-151 · routes/task_routes.py:85-238 ·
  routes/report_routes.py:12-101, 167-223
  Description: Nenhuma rota confere token. POST /users aceita role:'admin' vindo
  do cliente (52, 71). PUT /users/<id> troca role, active e senha de qualquer
  usuário (114-125). DELETE /users/<id> apaga em cascata. O token do login nunca
  é verificado.
  Impact: Qualquer cliente anônimo consegue virar admin, tomar contas alheias e
  destruir dados.
  Recommendation: Middleware de auth fail-closed com token assinado + checagem
  de dono/role (P-03).

  #4 [HIGH] Hash fraco / auth falsa (AP-09)

  File: models/user.py:29, 32 · routes/user_routes.py:64, 115, 210
  Description: hashlib.md5 sem salt; senha mínima de 4 caracteres; token
  'fake-jwt-token-' + str(user.id), que é previsível.
  Impact: Dá para forjar o token de qualquer usuário, e as senhas saem
  facilmente de um vazamento.
  Recommendation: werkzeug.security + token assinado com itsdangerous. As duas
  já vêm como dependência do Flask (P-09).

  #5 [HIGH] Fat Controller (AP-06)

  File: routes/report_routes.py:12-155 · routes/task_routes.py:11-63, 85-223,
  273-299 · routes/user_routes.py:42-90, 134-151
  Description: Handlers de 50 a 88 linhas com validação, regra de atraso e taxa
  de conclusão (reimplementadas 6×), agregações, cascata e serialização. O CRUD
  de categorias está dentro de report_routes.py.
  Impact: Essas regras não dão para testar isoladas e já começam a divergir
  entre as cópias.
  Recommendation: Services + controllers, com um blueprint próprio para
  categorias (P-06).

  #6 [HIGH] Acoplamento forte / sem DI (AP-07)

  File: routes/task_routes.py:2-5 · routes/user_routes.py:2-4 ·
  routes/report_routes.py:2-5
  Description: As rotas usam db.session e Model.query direto. Não há camada de
  serviço e nem application factory, e seed.py:2 importa app direto.
  Impact: Não dá para testar sem um banco real, e importar app cria as tabelas
  como efeito colateral.
  Recommendation: create_app(config) + services injetados (P-07).

  #7 [HIGH] Integridade — órfãos ao excluir categoria (AP-10)

  File: routes/report_routes.py:211-223 · models/task.py:14, 21
  Description: DELETE /categories/<id> não trata as tasks que referenciam a
  categoria. Como o SQLite não aplica FK por padrão, tasks.category_id fica
  apontando para um registro que não existe mais.
  Impact: Contagens e relatórios ficam inconsistentes.
  Recommendation: Na mesma transação, setar category_id = NULL nas tasks e
  depois remover a categoria (P-10).

  #8 [MEDIUM] Estado global mutável (AP-08)

  File: services/notification_service.py:6, 31-36, 43-48
  Description: A lista self.notifications = [] faz papel de "banco". Baixei de
  HIGH para MEDIUM porque a classe não é usada.
  Impact: Se for ligada, perde dados no restart e diverge entre workers.
  Recommendation: Serviço sem estado, com config injetada (P-08).

  #9 [MEDIUM] Queries N+1 (AP-11)

  File: routes/task_routes.py:41-57, 275-279 · routes/user_routes.py:22 ·

  Impact: A latência cresce junto com o volume de dados.
  Recommendation: selectinload + agregações com GROUP BY (P-11).

    gets its settings from config.

  - #10 MEDIUM AP-12: validation lives in utils/validators.py, with type checks.
    Bad input now returns 400 instead of 500.
  - #11 MEDIUM AP-13: there are no bare except: left. One central error handler
    always answers in JSON as {"error": ...}, including 404 and 405.
  - #12 MEDIUM AP-14: utcnow() is now a helper in utils/dates.py built on

  Contract changes (security-driven)
  1. All routes except GET /, GET /health, POST /login and POST /users now need
     a token (401 without one, 403 without the right role or ownership). You can
     turn this off for development with AUTH_REQUIRED=false, which logs a
     warning at boot.
  2. The password field is gone from user responses (GET/POST/PUT /users,
     /login).
  3. token is still the field name in the login response, but it is now a signed
     token. The old fake-jwt-token-<id> is rejected.
  4. POST /users with a role other than user requires an admin (403). New
     passwords need 8 or more characters (400).
  5. Error bodies: input that used to cause a 500 (wrong type) now gets a 400,
     and 404/405 come back as JSON instead of HTML.
