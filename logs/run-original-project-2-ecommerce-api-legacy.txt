  ## Findings

  ### #1 [CRITICAL] Hardcoded credentials / secrets (AP-02)
  File: src/utils.js:2-5
  File: src/AppManager.js:18, 45
  Description: The config holds production-looking secrets as literals: `dbPass:
  "senha_super_secreta_prod_123"`, `paymentGatewayKey:
  "pk_live_1234567890abcdef"`, `dbUser: "admin_master"`, `smtpUser`. The seed
  stores the user password `'123'` in plain text (line 18). Aggravating factor:
  the live gateway key is printed to the log on every checkout (line 45).
  Impact: Anyone with access to the repo or the logs gets a live payment key and
  DB credentials. Rotating them means a code change and a deploy.
  Recommendation: Move them to a `config` module that reads `process.env`, add a
  `.env.example` without real values, and never log secrets (Playbook P-02).

  ### #2 [CRITICAL] Administrative/destructive endpoints without authentication
  (AP-03)
  File: src/AppManager.js:80-129, 131-137
  Description: `GET /api/admin/financial-report` returns revenue and student
  names to anyone. `DELETE /api/users/:id` deletes any user with no
  authentication or authorization check (no owner or role check).
  Impact: Financial and personal data leaks. Any anonymous client can delete any
  account.
  Recommendation: Add fail-closed auth middleware (admin token from env; missing
  token → 401/403) on both routes, with an explicit dev opt-out only (Playbook
  P-03).

  ### #3 [CRITICAL] God Class (AP-04)
  File: src/AppManager.js:4-139
  Description: `AppManager` (generic name, ~135 lines) concentrates the DB
  connection (l.7), schema and seed (l.10-23), raw SQL, business rules (payment,
  hashing, enrollment), route registration (l.25-137) and response formatting,
  for 4 domains (users, courses, enrollments, payments).
  Impact: Nothing can be tested in isolation. Any change risks the whole app. No
  reuse across layers.
  Recommendation: Split into config / db / models (repositories) / services /
  controllers / routes / middlewares (Playbook P-04).

  ### #4 [CRITICAL] Sensitive data exposed in logs (AP-05)
  File: src/AppManager.js:45
  Description: `console.log(`Processando cartão ${cc} na chave
  ${config.paymentGatewayKey}`)` logs the **full card number (PAN)** together
  with the gateway key.
  Impact: PCI-DSS violation. Anyone with log access can read card data.
  Recommendation: Never log the PAN (at most the last 4 digits, masked) or
  secrets. Use a structured logger (Playbook P-05 / P-16).

  ### #5 [HIGH] Business logic in the route / callback hell (AP-06)
  File: src/AppManager.js:28-78, 80-129
  Description: The checkout handler (~50 lines, 5 nesting levels) decides
  payment status (`cc.startsWith("4") ? "PAID" : "DENIED"`, l.46), creates the
  user, hashes the password, enrolls, records the payment and writes the audit
  log, all inside HTTP callbacks. The report aggregates revenue inside the
  handler (l.89-127) using manual counters (`coursesPending`, `enrPending`).
  Impact: Rules can't be tested without HTTP, the flow is hard to follow, and
  there is a risk of double responses or lost responses.
  Recommendation: Extract `CheckoutService`/`ReportService` with async/await;
  controllers only translate HTTP ↔ service (Playbook P-06).

  ### #6 [HIGH] Tight coupling / no dependency injection (AP-07)
  File: src/AppManager.js:1, 7, 37, 40, 50, 54, 57, 69, 83, 92, 104, 106, 133
  File: src/app.js:8-10
  Description: The class creates its own connection (`new
  sqlite3.Database(':memory:')`) and the routes use `this.db`/`self.db`
  directly. `app.js` instantiates `AppManager` with no way to inject a different
  database.
  Impact: The database can't be swapped in tests. Persistence is coupled to the
  HTTP layer.
  Recommendation: The composition root creates the db and injects it into
  repositories → services → controllers (Playbook P-07).

  ### #7 [HIGH] Mutable global state (AP-08)
  File: src/utils.js:9-10, 14, 25
  Description: Module-level `let globalCache = {}` and `let totalRevenue = 0`,
  exported in `module.exports`. `logAndCache` writes to the cache on every
  checkout and the cache grows without bound (`last_checkout_${userId}`).
  Impact: Unbounded memory growth, hidden state shared across requests,
  nondeterministic tests.
  Recommendation: Remove the global cache (it is never read). If a cache is
  needed, inject an instance with a bounded size and TTL (Playbook P-08).

  ### #8 [HIGH] Weak password hashing / fake authentication (AP-09)
  File: src/utils.js:17-23
  File: src/AppManager.js:18, 35, 40, 66-75
  Description: `badCrypto` repeats the first 2 base64 characters of the password
  10,000 times and truncates to 10. The "hash" is reversible and collides for
  every password with the same prefix (`"senhaforte"` and `"se..."` produce the
  same hash). Default password `p || "123456"` (l.68). `pwd` is not required
  (l.35). Checkout reuses an existing account **by email alone, without checking
  the password** (l.40, 74). Seed password stored in plain text (l.18).
  Impact: Stolen credentials are trivially recovered. Anyone can buy, and create
  enrollments, in another user's account just by knowing their email.
  Recommendation: `crypto.scrypt` with a random salt (Node stdlib, no new
  dependency) plus `timingSafeEqual`. Require `pwd`, verify the password when
  the email already exists, and hash the seed (Playbook P-09).

  ### #9 [HIGH] Data integrity / missing transactions (AP-10)
  File: src/AppManager.js:12-16, 50-63, 131-136
  Description: Enrollment, payment and audit log are 3 writes with no
  transaction (l.50-61): if the payment fails, the enrollment stays orphaned.
  `DELETE /users/:id` ignores `err`, always returns 200 even for a nonexistent
  id, and leaves enrollments and payments orphaned (the response message admits
  it: "ficaram sujos no banco"). Schema has no `UNIQUE(email)`, no `FOREIGN KEY`
  and no `UNIQUE(user_id, course_id)`, so duplicate enrollments are allowed.
  Impact: Inconsistent data, a financial report with orphan entries, and
  duplicate accounts and enrollments.
  Recommendation: `BEGIN/COMMIT/ROLLBACK` in checkout, FKs with `ON DELETE
  CASCADE` + `PRAGMA foreign_keys=ON`, `UNIQUE` constraints, and check
  `err`/`changes` on delete (Playbook P-10).

  ### #10 [MEDIUM] N+1 queries (AP-11)
  File: src/AppManager.js:83, 89-106
  Description: For each course, `SELECT * FROM enrollments` (l.92), and for each
  enrollment, 2 more queries (`users` l.104, `payments` l.106). That is 1 + C +
  2E queries.
  Impact: Cost grows linearly with data volume, and the in-memory join is
  fragile.
  Recommendation: A single `LEFT JOIN` courses⋈enrollments⋈users⋈payments, then
  group in the service (Playbook P-11).

  ### #11 [MEDIUM] Missing input validation (AP-12)
  File: src/AppManager.js:29-35, 46, 132
  Description: Only presence is checked (`!u || !e || !cid || !cc`). There is no
  type check: `card` sent as a number → `cc.startsWith is not a function`
  throws inside the sqlite callback → **uncaught exception that kills the 
  process** (l.46). No email format check, `pwd` optional, `:id` not validated
  as an integer (l.132).
  Impact: Remote DoS with a single request. Malformed data reaches the database.
  Recommendation: A validation function in the routes layer (types, email,
  required pwd, integer id) → 400 (Playbook P-12).

  ### #12 [MEDIUM] Inconsistent error handling (AP-13)
  File: src/AppManager.js:38, 41, 57, 70, 92-93, 104-106, 133
  Description: No global error middleware. Plain-text errors (`"Erro DB"`, `"Bad
  Request"`) instead of JSON. DB error turned into 404 (l.38). `err` ignored at
  l.57, 92 (`enrollments.length` on `undefined` → crash), 104, 106, 133.
  Impact: Swallowed failures, crashes, and an inconsistent error format for
  clients.
  Recommendation: async handlers + `(err, req, res, next)` middleware + an
  `AppError` class with status (Playbook P-13).

  ### #13 [MEDIUM] Deprecated/obsolete APIs (AP-14)
  File: src/AppManager.js:26, 37-77, 83-128, 133
  Description: sqlite3's nested-callback API (up to 5 levels) and the `const
  self = this` idiom (l.26) used to work around `function` scope in callbacks.
  Impact: Hard to read, error propagation is error-prone, and try/catch isn't
  possible.
  Recommendation: Promise wrapper (`util.promisify`/small `run/get/all` adapter)
  + async/await (Playbook P-14).

  ### #14 [MEDIUM] Configuration coupled to code (AP-15)
  File: src/utils.js:6
  File: src/AppManager.js:7
  Description: Literal port `3000`, `':memory:'` fixed in the constructor. No
  environment variable is read anywhere.
  Impact: Can't change port or database per environment without editing code.
  Recommendation: `PORT`, `DB_PATH` from env with dev defaults in the config
  module (Playbook P-02).

  ### #15 [MEDIUM] Blocking side effects in the request (AP-16)
  File: src/utils.js:17-23
  File: src/AppManager.js:45-46, 68
  Description: `badCrypto` runs a 10,000-iteration loop with string
  concatenation and `Buffer.from` **synchronously** on the event loop on every
  checkout of a new user. The payment gateway is simulated inline in the
  handler.
  Impact: Blocks every concurrent request. The gateway can't be replaced or
  mocked.
  Recommendation: Async `crypto.scrypt` (runs on the libuv threadpool) and a
  `paymentGateway` injected into the service (Playbook P-06 / P-09).

  ### #16 [LOW] Magic numbers / strings (AP-17)
  File: src/AppManager.js:21, 46, 48, 68, 108
  File: src/utils.js:6, 19
  Description: Approval prefix `"4"`, statuses `"PAID"`/`"DENIED"` repeated,
  default `"123456"`, `10000` iterations, port `3000`.
  Impact: Rules are spread out and hard to find or change.
  Recommendation: Named constants (`PAYMENT_STATUS`, `APPROVED_CARD_PREFIX`)
  (Playbook P-15).

  ### #17 [LOW] Poor names (AP-18)
  File: src/AppManager.js:4, 29-33
  File: src/utils.js:12, 17
  File: src/app.js:13
  Description: Variables `u, e, p, cid, cc`. Class `AppManager`. `badCrypto`.
  `logAndCache` (does two things). Boot log "Frankenstein LMS". (The contract
  fields `usr/eml/pwd/c_id/card` are kept and only mapped internally.)
  Impact: Code is hard to read.
  Recommendation: Descriptive internal names. Map the request DTO to domain
  names in the controller (Playbook P-15).

  ### #18 [LOW] Logging with console.log (AP-19)
  File: src/AppManager.js:45
  File: src/utils.js:13
  Description: `console.log` used as a logging mechanism inside the business
  flow, with no level or structure.
  Impact: Noise, no way to filter or redact.
  Recommendation: A minimal logger module (levels) + request logging middleware
  (Playbook P-16).

  ### #19 [LOW] Dead code / unused exports (AP-20)
  File: src/utils.js:2-3, 5, 9-10, 25
  File: src/AppManager.js:2
  Description: `totalRevenue` imported (AppManager l.2) and never used.
  `globalCache` exported and never read. `dbUser`, `dbPass`, `smtpUser` never
  referenced. Table `audit_logs` written but never read (kept, since it is a
  legitimate audit trail).
  Impact: Confusion about what is actually used, and attack surface (dead
  secrets).
  Recommendation: Remove unused symbols (Playbook P-15).

  ## Contract changes (security-driven)
  - GET /api/admin/financial-report and DELETE /api/users/:id now require the 
  X-Admin-Token header (401 when missing or wrong; 403 when ADMIN_TOKEN is not 
  configured). The legacy open behaviour only comes back with 
  AUTH_REQUIRED=false.
  - POST /api/checkout: `pwd` is now required (400 "Bad Request"); an existing 
  email with the wrong password → 401 "Credenciais inválidas" (the legacy code 
  let anyone buy using someone else's account).
  - POST /api/checkout: a repeated enrollment (same user + course) → 409 instead
