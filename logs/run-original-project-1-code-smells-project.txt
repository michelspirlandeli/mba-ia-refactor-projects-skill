  ## Findings

  ### #1 [CRITICAL] SQL Injection (AP-01)
  File: models.py:28, 47-50, 57-61, 68, 92, 109-111, 126-129, 140, 148-151, 155,
  157-166, 174, 188, 192, 220, 224, 279-281, 289-299
  Description: Almost every query is built by joining strings with request data,
  e.g.
  `"SELECT * FROM usuarios WHERE email = '" + email + "' AND senha = '" + senha 
  + "'"` (login),
  `"UPDATE pedidos SET status = '" + novo_status + "'..."`, and the search
  `" AND (nome LIKE '%" + termo + "%' ..."` built from the `q` query string.
  Impact: Login bypass (`' OR '1'='1`), reading, changing or deleting any table,
  and dumping every user's password.
  Recommendation: Use `?` placeholders with a parameter tuple in every query, 
  including the dynamic search (Playbook P-01).

  ### #2 [CRITICAL] Hardcoded credentials / secrets (AP-02)
  File: app.py:7
  File: controllers.py:289
  File: database.py:75-78
  Description: `SECRET_KEY = "minha-chave-super-secreta-123"` is a literal in 
  the code. The same value is
  returned in the `/health` response (aggravating factor). The seed creates 
  `admin@loja.com` / `admin123` in plain text.
  Impact: Anyone who calls `/health` gets the app secret. A predictable admin 
  account exists in every environment.
  Recommendation: Read secrets from environment variables in a `config.py` + 
  `.env.example`, never serialize them, and seed with a hash (Playbook P-02).

  ### #3 [CRITICAL] Arbitrary execution / unauthenticated admin endpoints 
  (AP-03)
  File: app.py:11-28, 47-57, 59-78
  Description: `POST /admin/query` runs `cursor.execute(query)` on the client's 
  `dados.get("sql")`.
  `POST /admin/reset-db` wipes all 4 tables. None of the routes check auth: 
  anyone can call `DELETE /produtos/<id>`,
  `PUT /pedidos/<id>/status`, `GET /usuarios` (with passwords) and `GET 
  /relatorios/vendas` (financial data).
  Impact: Total compromise of the database by any anonymous client (read, write,
  DROP).
  Recommendation: Remove the arbitrary-SQL endpoint. Protect admin and 
  destructive routes with a fail-closed admin token or role, and check 
  ownership/role per resource (Playbook P-03).

  ### #4 [CRITICAL] God File (AP-04)
  File: models.py:1-314
  File: app.py:1-88
  File: database.py:7-86
  Description: `models.py` (314 lines) covers all 4 domains and mixes SQL, 
  business rules (discount bands,
  order total calculation) and response formatting. `app.py` holds config, 
  routes and handlers with inline SQL.
  `database.py` combines connection, DDL and seed in a single function.
  Impact: Each domain can't be tested or changed in isolation, and every change 
  risks side effects elsewhere.
  Recommendation: Split into config/, models/ (per entity), services/, 
  controllers/, routes/ (Blueprints) and db/ (connection, schema, seed) 
  (Playbook P-04).

  ### #5 [CRITICAL] Sensitive data exposed in responses (AP-05)
  File: models.py:83, 99
  File: controllers.py:285-289
  Description: `get_todos_usuarios` and `get_usuario_por_id` serialize `"senha":
  row["senha"]`, which is returned by
  `GET /usuarios` and `GET /usuarios/<id>`. `/health` returns `secret_key`, 
  `debug` and `db_path`.
  Impact: Mass credential leak and infrastructure details exposed to the public.
  Recommendation: Serialize users without `senha`. Limit `/health` to status and
  counts (Playbook P-05).

  ### #6 [HIGH] Business rules in the wrong layer (AP-06)
  File: controllers.py:24-58, 64-96, 188-220, 237-255
  File: models.py:139-146, 256-262
  Description: Controllers hold the product rules (price, stock, name length, 
  valid categories) and the order status
  transitions. On `cancelado` they only print "Devolver estoque" and never 
  restore the stock.
  The data layer computes the order total and the report's discount bands (`> 
  10000 → 10%`).
  Impact: Rules are scattered and impossible to unit test. Cancelled orders 
  silently lose stock.
  Recommendation: Create `services/` (produto_service, pedido_service, 
  relatorio_service) to hold the rules and make cancellation restore stock 
  (Playbook P-06).

  ### #7 [HIGH] Tight coupling / no dependency injection (AP-07)
  File: controllers.py:3, 264-274
  File: app.py:4, 49-55, 66-69
  File: models.py:1, 5, 25, 44, ... (every function calls `get_db()`)
  Description: Controllers and `app.py` import `get_db` from the driver and run 
  SQL directly (`health_check`, `reset_database`).
  Every model function pulls the global connection.
  Impact: The database can't be swapped in tests, and the layers depend on 
  infrastructure.
  Recommendation: Connection per request via `flask.g` + `teardown_appcontext`, 
  with SQL accessed only through models/repositories (Playbook P-07).

  ### #8 [HIGH] Mutable global state (AP-08)
  File: database.py:4, 8-10
  Description: Module-level `db_connection = None`, mutated with `global 
  db_connection`, and one connection
  shared across threads with `check_same_thread=False`.
  Impact: Race conditions and transactions interleaving between concurrent 
  requests in Flask's threaded server.
  Recommendation: One connection per request/app context, closed in teardown 
  (Playbook P-08).

  ### #9 [HIGH] Plain-text passwords / fake auth (AP-09)
  File: models.py:109-111, 126-129
  File: controllers.py:146-162, 167-186
  File: database.py:75-78
  Description: Passwords are stored as plain text, and login compares `senha = 
  '<input>'` in the SQL.
  `criar_usuario` has no minimum password policy. `/login` returns no token, so 
  the API has no way to
  authenticate later requests. There is no rate limiting.
  Impact: A leaked DB (see #1, #3, #5) exposes real passwords. Authorization is 
  impossible.
  Recommendation: Use 
  `werkzeug.security.generate_password_hash`/`check_password_hash` (already a 
  Flask dependency), a minimum of 8 characters, and a signed token 
  (`itsdangerous`, a Flask dependency) (Playbook P-09).

  ### #10 [HIGH] Data integrity / missing transactions (AP-10)
  File: models.py:65-70, 133-169, 275-283
  File: database.py:26-35, 45-53
  Description: `criar_pedido` checks stock and then decrements it later with no 
  atomic condition (race → negative stock).
  It accepts `quantidade` ≤ 0 (a negative quantity *adds* stock and reduces the 
  total). It doesn't check that `usuario_id` exists,
  and an early `return` leaves no rollback. `deletar_produto` orphans 
  `itens_pedido`. `atualizar_status_pedido` returns
  success for an order that doesn't exist. There is no `UNIQUE` on 
  `usuarios.email` and no FKs.
  Impact: Inconsistent stock and totals, duplicate accounts, orphaned data.
  Recommendation: Explicit transaction with rollback, conditional `UPDATE ... 
  WHERE estoque >= ?`, input validation, 404 for missing orders, soft delete 
  (`ativo=0`) for products that have orders, and a unique index on email 
  (Playbook P-10).

  ### #11 [MEDIUM] N+1 queries (AP-11)
  File: models.py:154-156, 187-199, 219-231, 239-254
  Description: `get_pedidos_usuario` and `get_todos_pedidos` run 1 query per 
  order plus 1 per item (`cursor2`/`cursor3`).
  `criar_pedido` re-queries the price in its second loop. The report runs 5 
  separate `COUNT`/`SUM` queries.
  Impact: Latency grows linearly with the number of orders and items.
  Recommendation: A `JOIN` between itens_pedido and produtos with `IN (...)`, 
  grouped in memory, plus a single aggregate query with `CASE` (Playbook P-11).

  ### #12 [MEDIUM] Missing / duplicated input validation (AP-12)
  File: controllers.py:28-54, 72-90, 118-121, 150-158, 169-170, 195-201, 239-242
  Description: `login` and `atualizar_status_pedido` call `dados.get` without 
  checking for `None` (→ 500). `preco < 0` with a string
  raises a TypeError (→ 500). `float(preco_min)` with bad input → 500. The 
  create/update validation is copied, and the copy in update
  drops the name length and category checks. Order items aren't type-checked 
  (`item["produto_id"]` raises KeyError).
  There is no email format check.
  Impact: 500s for client errors, and invalid data (an invalid category) can get
  in through PUT.
  Recommendation: A single validation module/schema reused by create and update,
  returning 400 (Playbook P-12).

  ### #13 [MEDIUM] Inconsistent error handling (AP-13)
  File: controllers.py:10-12, 21-22, 60-62, 95-96, 108-109, 125-126, 133-134, 
  143-144, 164-165, 185-186, 218-220, 226-227, 234-235, 254-255, 261-262, 
  291-292
  File: app.py:77-78
  Description: `except Exception as e: return jsonify({"erro": str(e)}), 500` is
  repeated in every handler and leaks internal
  details (SQL messages). There is no `@app.errorhandler`, so an unknown route 
  returns Flask's default HTML.
  Impact: Internals leak to clients, error formats are inconsistent, and the 
  code is duplicated.
  Recommendation: Domain exceptions (`NotFoundError`, `ValidationError`) plus a 
  central JSON error handler that logs the stack trace (Playbook P-13).

  ### #14 [MEDIUM] Config hardcoded in the code (AP-15)
  File: app.py:8-9, 88
  File: database.py:5
  File: controllers.py:286-288
  Description: `DEBUG = True` and `app.run(host="0.0.0.0", port=5000, 
  debug=True)` are fixed. With debug on and bound to `0.0.0.0`,
  the Werkzeug console is exposed. `CORS(app)` allows any origin. `db_path = 
  "loja.db"` and `"ambiente": "producao"` are literals.
  Impact: The interactive debugger (remote execution) is reachable on the 
  network, and nothing can be configured per environment.
  Recommendation: `config.py` reading `FLASK_DEBUG`, `HOST`, `PORT`, 
  `DATABASE_PATH` and `CORS_ORIGINS` from the environment (Playbook P-02).

  ### #15 [MEDIUM] Synchronous side effects in the request flow (AP-16)
  File: controllers.py:208-210, 247-250
  Description: Email/SMS/push "sending" is simulated with `print` inside the 
  order controller. Status notifications are inline.
  Impact: Integrations are coupled to the HTTP handler, and a real integration 
  would block the request.
  Recommendation: Extract a `notification_service` called by the service layer 
  (Playbook P-06).

  ### #16 [LOW] Magic numbers / strings (AP-17)
  File: models.py:256-262
  File: controllers.py:47-50, 52, 242
  File: app.py:36, 88
  Description: Discount bands `10000/5000/1000` and rates `0.1/0.05/0.02`, name 
  limits `2`/`200`, category and status lists as
  literals, port `5000`, version `"1.0.0"` duplicated in app.py and 
  controllers.py.
  Impact: Rules are hard to find and change consistently.
  Recommendation: Named constants in `config`/domain modules (Playbook P-15).

  ### #17 [LOW] Poor names (AP-18)
  File: models.py:187-193, 219-225
  File: controllers.py:56, 160
  Description: `cursor2`, `cursor3` and `prod` in the loops. The variable `id` 
  shadows the Python builtin.
  Impact: Readability.
  Recommendation: Descriptive names (`produto_id`, `itens_rows`) without 
  renaming contract fields (Playbook P-15).

  ### #18 [LOW] Logging with print / personal data in logs (AP-19)
  File: controllers.py:8, 11, 57, 61, 106, 161, 179, 182, 208-210, 219, 248, 250
  File: app.py:56, 83-86
  Description: `print` is the only logging mechanism, and it writes user emails 
  (`"Login bem-sucedido: " + email`, `"Usuário criado: " + email`).
  Impact: No log levels or structure, and personal data ends up in stdout.
  Recommendation: The `logging` module with a configurable level, without PII 
  (Playbook P-16).

  ### #19 [LOW] Dead code / duplication (AP-20)
  File: models.py:2, 12-21, 31-40, 304-313, 171-233
  File: database.py:2
  Description: `import sqlite3` (models) and `import os` (database) are unused. 
  The product serialization is copied 3 times.
  `get_pedidos_usuario` and `get_todos_pedidos` are near-identical copies.
  Impact: Maintenance drift (a fix in one copy doesn't reach the other).
  Recommendation: `_row_to_produto` / `_load_pedidos(where)` helpers and remove 
  the unused imports (Playbook P-15).
